# Bootstrapping FluxCD

How Flux was installed on the k3s cluster so that this repository drives what runs on it. Done 2026-10-14 with Flux v2.9.6, following the KubeCraft Kubernetes Homelab course and the [Flux docs](https://fluxcd.io/flux/installation/bootstrap/github/).

## Layout

```
clusters/
└── staging/
    └── flux-system/
        ├── gotk-components.yaml   # Flux itself: CRDs and the four controllers
        ├── gotk-sync.yaml         # GitRepository + Kustomization pointing back at this repo
        └── kustomization.yaml
```

Everything under `flux-system/` is generated by `flux bootstrap` and is never edited by hand. Apps, infrastructure and monitoring are added next to it as one Flux Kustomization file each (`apps.yaml`, `infrastructure.yaml`, `monitoring.yaml`).

## Steps

1. **Install the CLI** with mise, which manages my CLI tools on both laptops:
   ```bash
   mise use -g flux2@latest
   flux version --client
   ```
2. **Point kubectl at the right cluster.** My workstation also has a local Rancher Desktop cluster, and bootstrap installs into whichever context is current:
   ```bash
   kubectl config use-context homelab
   kubectl get nodes
   ```
3. **Pre-flight check:**
   ```bash
   flux check --pre
   ```
4. **Create a fine-grained GitHub token** limited to this repository, valid for 7 days, with Administration read/write, Contents read/write and Metadata read-only.
5. **Bootstrap:**
   ```bash
   read -rs GITHUB_TOKEN && export GITHUB_TOKEN    # not echoed, not saved in history
   export GITHUB_USER=turpinator-x
   flux bootstrap github \
     --owner=$GITHUB_USER \
     --repository=homelab \
     --branch=main \
     --path=./clusters/staging \
     --personal \
     --token-auth=false
   unset GITHUB_TOKEN
   ```
6. **Verify:**
   ```bash
   git pull                       # bootstrap pushed two commits from its own clone
   flux check
   flux get all -A
   kubectl get pods -n flux-system
   ```

## Design choices

- **Deploy key instead of a stored token.** By default Flux keeps the GitHub token in the cluster and uses it for every pull. With `--token-auth=false`, the token is used once to push the manifests and register a read-only SSH deploy key, and the cluster pulls with that key from then on. The `flux-system` Secret holds only the SSH key pair and `known_hosts`. The token can expire or be revoked without affecting the cluster; a new one is only needed to re-run bootstrap.
- **Fine-grained, short-lived token.** Scoped to one repository instead of every repo a classic `repo` token can reach, and expiring in days because it's only needed for a few seconds.
- **Pull, not push.** Flux inside the cluster pulls from GitHub, so GitHub never needs network access to my LAN.
- **`clusters/<name>` layout.** One repository can manage several clusters (for example staging and production), each with its own folder.
